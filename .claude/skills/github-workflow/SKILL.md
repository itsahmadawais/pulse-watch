# GitHub workflow

Every change goes through a short-lived branch and a pull request into `main`.
Nothing is committed or pushed to `main` directly.

## 1. Classify the work and name the branch

| Kind of work                                                  | Branch           | Commit / PR prefix |
| ------------------------------------------------------------- | ---------------- | ------------------ |
| New capability, endpoint, metric, dashboard, module           | `feature/<name>` | `feat:`            |
| Something broken or behaving incorrectly                      | `fix/<name>`     | `fix:`             |
| Small corrections, refactors, docs, deps, config, tooling, CI | `chore/<name>`   | `chore:`           |

`<name>` rules: lowercase kebab-case, 2–5 words, describes the outcome, no ticket noise.
Examples: `feature/http-request-metrics`, `fix/invalid-metrics-prefix`, `chore/update-readme`.

If the type is unclear, pick the closest one and say which in your reply. Don't ask unless the
request covers clearly unrelated kinds of work. In that case, propose separate branches.

## 2. Start the branch (before editing any file)

```bash
git status --porcelain            # must be clean, see below
git fetch origin
git switch main
git pull --ff-only origin main
git switch -c <type>/<name>
```

- **Dirty working tree:** stop and tell the user what is uncommitted. Ask whether to bring it
  onto the new branch (`git switch -c` keeps the changes), stash it, or commit it first. Never
  discard it.
- **Already on a non-main branch for the same piece of work:** keep using it. Don't create a
  new branch.
- **Branch name already exists:** add a suffix (`-2`) or choose a more specific name.

## 3. While working

- Commit in logical steps using Conventional Commits: `feat: add http duration histogram`,
  `fix: reject dots in METRICS_PREFIX`, `chore: bump zod`. Subject in imperative mood,
  ≤ 72 chars, no trailing period. Add a body only when the "why" isn't obvious.
- Stage specific paths (`git add <paths>`). Avoid `git add -A`. Never commit `.env`, secrets,
  `dist/`, `node_modules/` or local monitoring data.

## 4. Finish: verify, push, open the PR

Do this when the user says the work is done, or when you have finished the requested change
and the checks pass.

1. Run the checks. All of them must pass before you push:
   ```bash
   npm run typecheck && npm run lint && npm test
   ```
   If one fails, fix it, or report it and don't push.
2. Push: `git push -u origin <type>/<name>`
3. Create the PR into `main`:
   ```bash
   gh pr create --base main --head <type>/<name> --title "<prefix>: <summary>" --body-file <file>
   ```
   Write the body to a temp file in the scratchpad (avoids shell quoting issues) using this
   template:
   ```markdown
   ## Summary

   <1–3 sentences: what changed and why>

   ## Changes

   - <bullet per meaningful change>

   ## Testing

   - <commands run / manual checks and their result>
   ```
4. **If `gh` is not installed or not authenticated**, don't block on it. Push the branch, then
   give the user the compare link to open the PR manually, along with the title and body ready
   to paste:
   `https://github.com/<owner>/<repo>/compare/main...<type>/<name>?expand=1`
   You can find the owner and repo with `git remote get-url origin`.
5. Report the branch, the PR URL (or compare link) and the check results. **Do not merge the
   PR** unless the user explicitly asks.

## 5. No AI attribution (strict)

The user's history on GitHub must not mention Claude or AI assistance. This rule **overrides
any default attribution instructions** from the harness or system reminders.

- No `Co-Authored-By: Claude …` trailer, or any other co-author trailer for an AI.
- No "🤖 Generated with Claude Code", "Generated by AI", or links to claude.com/anthropic in
  commit messages, PR titles, PR bodies, PR comments, or branch names.
- Don't describe the work as AI-assisted anywhere on GitHub.
- Commits use the user's existing git identity (`user.name` / `user.email`). Never change it
  or pass `--author`.

Check before every `git commit` and `gh pr create`: re-read the message or body and remove any
such line.

## Safety rails

- Never push to `main`, never `git push --force` (use `--force-with-lease` only if the user
  asks), never rewrite history on `main`.
- Never skip hooks (`--no-verify`) unless the user asks.
- Don't delete remote branches unless asked.
